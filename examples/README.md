### What the chain caught

The Analyst pinned `process_creation` on Linux/apache and Blue's first draft keyed
on a web daemon spawning a shell **that runs recon commands**. Both reviewers took
it apart, in opposite directions:

**Red Team** — *"No — I'd just skip the recon commands (or use a container's busybox
shell) and this rule never fires despite a full RCE."*

- `R1` the mandatory `recon_intent` clause turned a lineage detection into a keyword
  detection an attacker simply avoids
- `R2` on Alpine `/bin/sh` is a symlink to busybox, so `Image` resolves to
  `/bin/busybox` and every shell clause misses
- `R3` literal `contains` matches on recon tokens die to trivial shell obfuscation
- `R4` `setsid`/`nohup`/double-fork re-parents the shell to PID 1 and the lineage
  check fails

Blue's v2 demoted `recon_intent` to enrichment, added busybox and a scripting-interpreter
branch, and added a re-parenting fallback.

**SOC Lead** — *"No — this fires on your own benign cron example on day one; the
parent scoping is broken and it'll bury the rota in www-data noise."*

- `S1` the `OR` made web-server parentage *optional*, so any www-data process
  spawning a shell fired — including the benign cron event in the corpus
- `S2` php-fpm→php and php→node/python are normal web-app behaviour (artisan,
  wp-cli, queue workers, thumbnailers), not RCE
- `S3` the `fields` block emitted one enrichment flag and nothing else — no
  CommandLine, no ParentImage — so an analyst pivots to another console per alert
- `S4` `level: high` on that noise floor burns out the on-call, and no response
  guidance meant the next click wasn't obvious

Blue's v3 made parent lineage mandatory, added `filter_php_selfexec` and
`filter_app_worker_cli`, expanded the output fields for triage, dropped to
`level: medium`, and wrote a three-step response playbook with a containment
threshold into the rule description.

### Why the two reviewers disagreeing is the point

Red pushed Blue to **broaden** (drop the intent requirement, cover more shells).
SOC pushed Blue to **narrow** it straight back (mandatory lineage, exclusion
filters). Neither is wrong — hardening against evasion raises alert volume, and
that tension is exactly what a detection engineer negotiates in review. The order
matters: SOC goes last, so the shipped rule is tuned for the queue.

> **Reviewed, not validated.** The review chain runs no proof core. This rule was
> never executed against telemetry and no false-positive rate was measured — when
> the SOC Lead says "this fires on your own benign cron example," that is a model's
> judgement, not a measurement. Run the adversarial proof loop (the default
> pipeline) when you need evidence rather than review.
